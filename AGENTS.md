# Portable agent guide

Portable is a monorepo of small npm packages that run unchanged in browsers, Cloudflare Workers, Node, Bun, and Deno. Read [docs/architecture.md](docs/architecture.md) for how the repo is built, tested, and released, and [docs/packages.md](docs/packages.md) for the package plan. Decisions and the options considered are logged in [docs/decisions.md](docs/decisions.md), and tooling friction in [docs/papercuts.md](docs/papercuts.md). Add an entry to decisions.md when you make a choice the docs don't settle, and to papercuts.md when a tool costs you time.

## Commands

| Command | What it does |
| --- | --- |
| `pnpm check` | Format with oxfmt, lint with oxlint, and type-check, fixing what it can (`vp check --fix`). |
| `pnpm check:types` | `tsc -b` over every package, then `tsc -p tsconfig.test.json` over every `test/` directory. |
| `pnpm check:prose` | Runs `tools/lint/src/prose.test.ts`, which checks Markdown, comments, and test names for the patterns in [Writing](#writing) that a regular expression can find, and `tools/lint/src/packageLinks.test.ts`, which checks that pages link the packages they mention. The pre-push hook runs this. |
| `pnpm test` | All test projects: Node and browsers. |
| `pnpm test:bun`, `pnpm test:deno` | The conformance tests with Vitest running on Bun or Deno, which must be installed. |
| `pnpm test:workers` | Bundles every package into one Worker and runs `tools/workers/src/checks.ts` in workerd through Miniflare. |
| `pnpm test:changed` | Node tests affected by changes since `origin/main`. The pre-push hook runs this. |
| `pnpm fuzz` | Runs only the fuzz tests (`*.fuzz.conformance.ts` and `*.fuzz.oracle.test.ts`) in Node, with 10,000 runs per property instead of 100. |
| `pnpm bench` | Builds every package, then runs each package's benchmarks (`*.bench.ts`) against the built `dist/`, one package at a time, and saves the results in `.bench/`. Pass package names to `node scripts/bench.ts` to run only those. |
| `pnpm coverage` | Node tests with V8 coverage of `packages/*/src`, written to `coverage/coverage-summary.json`. |
| `pnpm readme` | Runs `pnpm bench` and `scripts/bundle-size.ts`, then `scripts/readme-stats.ts` rewrites the benchmark and stats tables in each package README. `scripts/readme-tables.ts` lists each table's columns and rows. |
| `pnpm build` | Builds every package with zile into `dist/`. |
| `pnpm changeset` | Records a version bump and changelog entry for the packages you changed. Until the first release, edit the package's `.changeset/<package>-initial.md` instead. |

Git hooks live in `.vite-hooks/` and are installed by `pnpm install`. The pre-commit hook formats and lints staged files, and the commit-msg hook rejects a message that describes a made-up actor or has a list without a serial comma (`tools/lint/src/commitMessage.ts`). The pre-push hook runs `vp check` without fixing, `pnpm check:prose`, and `pnpm check:types`, then the affected tests. On each push to `main`, and when someone starts it by hand, CI runs `vp check`, `pnpm check:types`, every test project, the conformance tests on Bun and Deno, and the workerd checks, and a run started by hand can also run `pnpm fuzz` (see [docs/architecture.md](docs/architecture.md#ci)). CI runs only for `main`, because the repo pays for each Actions minute. Don't start a run by hand to check a branch or a pull request: run `pnpm check`, `pnpm check:types`, and the tests locally, and leave CI for the merge to `main`.

## Package rules

- Use only the WinterTC common API: `fetch`, `Request`/`Response`, Web Streams, `TextEncoder`/`TextDecoder`, `Uint8Array`, `crypto.subtle`. No `node:*` imports, `Buffer`, `process`, or DOM globals. Lint enforces this outside `*.oracle.test.ts` and `*.bench.ts`.
- Don't rely on `ReadableStream.from` or `for await` over a `ReadableStream` in package code. Some browsers we support don't have them yet. Lint rejects `ReadableStream.from`, and `tools/lint/src/forAwait.test.ts` reads package code with the TypeScript checker and reports a `for await` over a value that can be a `ReadableStream`. A `for await` over a generator or another async iterable is fine.
- Package code targets ES2022, and because `lib` is ES2022, `tsc` rejects built-ins added later, such as `Array.prototype.findLast`. Don't add polyfills or patch globals. To use a newer API, check for it and fall back to your own code. For example, `Bytes.toHex` calls `Uint8Array.prototype.toHex` when the runtime has it and converts the bytes itself when it doesn't. Before you use a web API newer than the ones in the [runtime baseline](docs/architecture.md#runtime-baseline), add it to that table with its browser versions.
- No runtime dependencies outside `@portable/*`. Crypto defaults to WebCrypto, and the caller can pass @noble/hashes or another function instead. A package takes @noble/hashes as an optional peer only for what WebCrypto can't do, such as an incremental hash.
- Streaming transforms are `TransformStream` subclasses, used as `stream.pipeThrough(new Lines.DecoderStream())`. Wrap the transformer in `Streams.abortable(transformer, options)` to support the `signal` option.
- Each entry point is a file in `src/exports/` named after its subpath: `src/exports/index.ts` for `.` and `src/exports/internal.ts` for `./internal`. An entry file only re-exports from the modules beside it, and it is the only kind of file that re-exports, so there are no other barrel files. It may also re-export a type from another `@portable/*` package when the package's options use that type, as websockets does with `Timers.Delay`, so a caller doesn't need a second import. Code inside a package imports the module it needs, never a file in `src/exports/`, and lint rejects such an import.
- Each `package.json` `exports` entry is `{ "src": "./src/exports/<name>.ts", "types": "./dist/exports/<name>.d.ts", "default": "./dist/exports/<name>.js" }`. The `src` condition points the workspace at source, and the published package uses `types` and `default`. Only the fields after `"[!start-pkg]"` are published, so `name`, `description`, and `dependencies` go after it. Copy the field order of `packages/mail/package.json`: `scripts`, `"[!start-pkg]"`, `name`, `description`, `version`, `type`, `sideEffects`, `license`, `repository`, `keywords`, `engines`, `files`, `dependencies`, `exports`, `main`, `module`, `types`. Workspace dependencies are `workspace:*`.
- A `description` says what the package does in one sentence, starting with a verb where one fits, and ends with ", in any JavaScript runtime." smtp, which needs a TCP socket API, ends with ", in any JavaScript runtime that has a TCP socket API." `tools/lint/src/packages.test.ts` checks this, the field order, the `exports` map, that `dependencies` lists exactly the `@portable/*` packages the source imports, the test package, the changeset, and the README's first lines.
- A package exports a small API. Keep helpers private unless a caller needs them.
- When another `@portable/*` package needs a package's private building blocks, as arc needs dkim's canonicalization and signing, export them from an `./internal` subpath whose module JSDoc says it isn't public API and can change in any release. Only `@portable/*` packages import it, through a `workspace:*` dependency, which pnpm publishes as the exact version. Its exports need no `@example` and no README entry. Code that every package could use, such as `Bytes.concat`, goes in a shared package instead.
- A package README has these parts in order: the package name, a description ending in "Runs in browsers, Cloudflare Workers, Node 24+, Bun, and Deno.", a "Replaces" line; install and usage snippets; the API and its options; `## Types` for exported types; and `## Why use this over <the libraries it replaces>` (fixes, benchmarks, and differences from those libraries that you could miss when switching, such as a default or a count). There is no migration section, because the API sections already show each call. Every export appears in the README.

## API conventions

Every package follows the same shape, so once you know one, you know the rest.

- Callers import a package as a namespace: `import * as Base64 from '@portable/base64'`. Exports therefore use short names without the package name: `Base64.encode`, not `encodeBase64`. Named exports only.
- The namespace is the package name with each hyphenated word capitalized (web-push becomes `WebPush`), keeping the spelling of an established name (`OAuth1`). It must not shadow a global, which is why the packages are web-crypto and websockets and not crypto and websocket.
- A package's main factory is `create`, as in `RateLimit.create` and `Dns.create`, not `createResolver`, which repeats the namespace.
- A function that returns a boolean starts with `is`, `has`, or `can` (`Ip.canParse`, named after `URL.canParse`), unless a standard name exists, such as `equal` or `needsRehash`.
- Use the same verbs everywhere. `encode` and `decode` convert between a value and its bytes or text. `parse` reads a value out of bytes in one direction only, as image-size and exif do. `parse` and `format` are the pair for a text syntax with structure, such as an address list or a header value with parameters, where the text is meant to be read as well as decoded. A variant whose bytes or text are a stream adds `Stream`: `ImageSize.parseStream(stream)` reads one, and `JsonStream.encodeStream(value)` returns one. A sync variant of an async function adds `Sync`.
- Streaming transforms are `TransformStream` subclasses named after `TextDecoderStream`. A transform that reads bytes or text into values is `DecoderStream`, and one that writes values as bytes or text is `EncoderStream`, so `Lines.DecoderStream` splits bytes into lines as `Jsonl.DecoderStream` splits them into JSON values. Name a transform for what it does only when it neither decodes nor encodes. Generic operators that take a function or a number, like the array helpers, are lowercase factories instead: `Streams.map(fn)`, `Streams.limitBytes(n)`.
- Every `EncoderStream` and every `*Stream()` function that writes text emits `Uint8Array`, as `TextEncoderStream` and `CompressionStream` do, so its output can be a `Response` body. A one-shot `encode` that writes text, such as `Base64.encode` or `Csv.encode`, returns a string.
- Bytes are `Uint8Array` in and out, never `ArrayBuffer` or another view. Given a buffer or a view, a package can't tell which of its bytes the caller meant, so the caller converts the value to a `Uint8Array`, and the conversion in the caller's code shows which bytes the package reads ([decision](docs/decisions.md#byte-inputs-stay-uint8array-only)). Check byte input with `assertUint8Array` from `@portable/bytes/internal`, which throws a `TypeError` for anything else, and test for bytes with `isUint8Array`, never with `instanceof Uint8Array`, because `instanceof` returns false for a `Uint8Array` from another realm. A Node `Buffer` is a `Uint8Array` and is accepted. `assertUint8Array` also accepts a `Uint8Array` over a `SharedArrayBuffer`. `crypto.subtle`, `Blob`, `fetch`, `CompressionStream`, and `WebSocket.send` throw for shared memory, so pass bytes to them through `toBufferSource`, which copies a view of a `SharedArrayBuffer`. Functions that take text also take its bytes (`string | Uint8Array`). Text comes out as `string`. When a package creates bytes and returns them, type them as `Uint8Array<ArrayBuffer>`, because `crypto.subtle`, `Blob`, and `fetch` accept that as a `BufferSource`. A stream that passes its input chunks through keeps the input's type.
- Functions are sync unless the platform API they need is async, such as `crypto.subtle` or `CompressionStream`.
- Choose parameters with these three rules, in order:
  - When a function is the analogue of a platform function, copy that function's signature: `WebCrypto.digest(hash, data)` follows `crypto.subtle.digest`, and `Compress.crc32(data, previous?)` follows `zlib.crc32`.
  - The value being converted or acted on is positional, followed by one optional `options` object: `Base64.encode(bytes, options)`, `Timers.debounce(fn, ms)`, `Bytes.equal(a, b)`.
  - Inputs with distinct roles go in one object: `WebPush.send({ subscription, payload, vapid })`. Start with the object form if a function might later need another such input, because moving from positionals to an object breaks callers and adding an option doesn't.

  Outside the platform case there are no optional positionals, no rest parameters, no positional that accepts `undefined`, no positional booleans and no overloads keyed on argument count or on an option's value. When an option would change the result type, write two functions instead, as mime-headers does with `parseAddresses` and `parseMailboxes`. The exception is a generic inferred from the option, as csv's `header` types each row by its column names ([decision](docs/decisions.md#csvdecode-types-rows-by-the-header-names)).
- Durations are milliseconds unless the wire format sets the unit, as the Web Push protocol does for `ttl`, which is in seconds. An instant in options, such as `now` or `expiresAt`, has the type `Timers.Instant`, which is `Date | { readonly epochMilliseconds: number }`, so a caller can pass a `Temporal.Instant` or `Temporal.ZonedDateTime` where the runtime has Temporal. The package converts it with `toEpochMilliseconds` or `toDate` from `@portable/timers/internal`. Instants in results are `Date`, because Safari has no Temporal yet ([decision](docs/decisions.md#instants-accept-temporal-and-results-stay-date)). Every function that reads the clock takes `now` with that type, so a test can fix the time.
- A `fetch` option has the type `(request: Request) => Promise<Response>`, so one wrapper for logging, retries, or a test double works with every package. A package builds the `Request` itself and passes it to the `fetch` option.
- A pluggable crypto function uses a type from @portable/web-crypto (`WebCrypto.Digest`, `WebCrypto.Hmac`, `WebCrypto.Hasher`), takes the algorithm first, and is passed in an option named after the type, in lowercase (`hmac`, `digest`, `hasher`). The default is the WebCrypto implementation.
- Everything that can be cancelled takes `signal?: AbortSignal | undefined` in its options: every async function, every stream class, and anything that holds a timer, listener, socket, or reader. Pass one signal down, and when it aborts, every layer under it stops: `fetch` calls, timers, event listeners, readers, and nested streams. Aborting rejects with `signal.reason`, as `fetch` does, or errors the stream with it and cancels its source. Remove listeners on the signal when the work finishes. To stop waiting for a promise from code that takes no signal, such as a caller's resolver, wrap it in `abortable(promise, signal)` from `@portable/timers/internal`. Plain sync functions have nothing to interrupt and take no signal. Timeouts are left to `AbortSignal.timeout` and `AbortSignal.any` rather than a `timeout` option, unless the timeout covers one step of many (such as one retry attempt).
- An object that holds a socket, timer, listener, or running task after the call that created it returns, such as `Smtp.Client`, a `Queue.Queue`, or a debounced function, is torn down by a `close()` method, which returns a promise when the teardown is async, or by aborting the `signal` it was created with. A debounced function keeps lodash's name, `cancel()`, for its teardown. If the `signal` only limits how long the object takes to start, as `Smtp.connect`'s does, the object needs `close()` as well. Where the runtime has `Symbol.asyncDispose`, the object also has `[Symbol.asyncDispose]()`, which does the same teardown and settles when it is done, so a caller can write `await using client = await Smtp.connect(options)`. A teardown that is sync uses `Symbol.dispose` instead. `withAsyncDispose` and `withDispose` from `@portable/errors/internal` set the key only when the symbol exists, and type it so that the key appears only when the caller's TypeScript lib declares the symbol. Package code doesn't use `using` itself: with `target` ES2022, `tsc` turns it into calls to tslib helpers, and the build fails because tslib isn't installed ([decision](docs/decisions.md#long-lived-objects-have-symbolasyncdispose-where-the-runtime-has-it)).
- A function whose result a caller loops over returns a `ReadableStream` or an async iterable, never a callback or an event emitter, so the caller can write `for await (const row of rows)` where the runtime iterates streams, and `Streams.toAsyncIterable(rows)` where it doesn't. Examples that loop over a stream use `Streams.toAsyncIterable`, which works in every runtime we support.
- Errors are thrown, never returned. Each package subclasses the classes in @portable/errors where they fit: `TruncatedError` (input ended early), `InvalidInputError` (malformed input), `UnsupportedError` (valid input the package doesn't handle), `MaxBytesError`, `MaxLengthError`, and `ResponseError`. Add another error class, extending `Errors.BaseError`, only when a caller needs to tell it apart. An error for an exceeded size limit is named after the option, like `Streams.MaxBytesError` for `maxBytes`, and stores the limit. A `ResponseError` keeps the whole `Response`.
- An error thrown in place of another error, such as a `catch` that wraps a parse failure in `InvalidInputError`, passes the original as `cause`. A caller can then find the original error, which a message string alone loses.
- An error with only a message takes `(message?, options?)`, as `Error` does. An error with other fields takes one object, such as `new Dns.QueryError({ code, syscall, hostname, cause })`.
- Nothing a caller passes between packages, or between two copies of one package, may depend on module identity: `instanceof` against a class without `Symbol.hasInstance`, a module-private `Symbol()` key, or a module-level `WeakMap` registry. `workspace:*` publishes exact versions, and npm can't dedupe two different exact versions, so an app can end up with two copies of one `@portable/*` package. Store a mark as a property under a `Symbol.for('portable.…')` key instead, as the error brand and rpc's `withContext` do. `portable/no-private-symbol` rejects `Symbol()` in package code.
- Pick the error by what is wrong. Throw `InvalidInputError` when the data a function exists to read, parse, decode, encode, or verify is malformed: bytes that don't decode, a header that doesn't parse, a value that can't be encoded. That data often comes from outside the program, so callers catch this error. Throw the built-in `TypeError` when an argument or option has the wrong type or is missing, and `RangeError` when it has the right type but a value the function doesn't accept: a negative `maxBytes`; an unknown name in a string option; or a key or secret that doesn't parse. Those are mistakes in the calling code or its configuration, and the platform throws the same errors (`'a'.normalize('x')` throws a `RangeError`). Where a package mirrors a platform function, such as `JSON.stringify` in jsonl, it throws what that function throws.
- A size limit is `maxBytes` when it counts bytes and `maxLength` when it counts string length in UTF-16 code units, as `String.prototype.length` does. A limit on something else is named for it (`maxParts`, `maxQueued`). A decoder that buffers input until it reads a delimiter takes a size limit, which defaults to `Infinity`.
- Results are plain objects and arrays with documented types, not class instances.
- A function's result type is `fn.ReturnType` in the function's namespace, following ox. For an async function it is the resolved value: `send(): Promise<send.ReturnType>`. A factory returns a long-lived object whose top-level type is named for what it is (`Dns.create(): Dns.Resolver`). When a caller stores a domain type or verdict, or passes it to another function, the type has a top-level name, such as `MimeHeaders.Address`, `Spf.Result`, and `Dkim.Result`.

## Code style

These follow [wevm/ox](https://github.com/wevm/ox/blob/main/AGENTS.md).

- `type` over `interface`. `readonly T[]` in types, never `Array<T>` or `ReadonlyArray<T>` (`typescript/array-type` checks this). No enums (`portable/no-enum`).
- Write `const name = value satisfies Type`, not `const name: Type = value`, so the constant keeps the type TypeScript infers. An annotation is still right on an empty collection, as in `const chunks: Uint8Array[] = []`, because `[] satisfies Uint8Array[]` infers `never[]`, and when the wider type is the point: `unknown`, `unique symbol`, an index signature (such as a `Record`) that a lookup reads with any string, an object that the code later writes properties to or that refers to itself, an exported constant, or a value read through a wider view. The `portable/prefer-satisfies` lint rule in `tools/lint` checks this.
- Name a type parameter with a lowercase word that says what it holds, such as `chunk`, `value`, or `key`, not `T` or `Chunk`. The `portable/type-parameter-name` lint rule checks this.
- Options objects are `options: Options = {}` and are typed in a `declare namespace` named after the function or class (`DecoderStream.Options`).
- With `exactOptionalPropertyTypes`, write optional properties as `foo?: T | undefined`. `portable/optional-undefined` checks this and fixes it.
- Relative imports end in `.js` (`portable/import-extension`).
- Statements end with semicolons, and so do the statements in examples. oxfmt adds them to code (`semi: true` in `vite.config.ts`), and `tools/lint/src/examples.test.ts` checks the examples, which oxfmt doesn't format.
- Every `if`, `else`, and loop body goes in braces, even a one-line early `return`, and so do the bodies in examples. The `curly` lint rule checks the code, and `tools/lint/src/examples.test.ts` checks the examples.
- A helper that throws for an invalid value and otherwise returns nothing or the same value is named `assert*`, such as `assertSize` and `assertUint8Array`. A helper that also changes the value, such as trimming it or converting a domain to its A-label, is named for the change: `normalizeName`, `formatAddress`.
- Use classes only for errors and for subclasses of platform types. Error classes extend a class from @portable/errors and set `static override readonly kind: string`, which `BaseError` copies to `name`. Kinds are namespaced by package, like `'Lines.MaxLengthError'`. A package's error classes live in `src/errors.ts`. `portable/error-kind` checks that each error class sets `kind`.
- Public functions, classes, and constants, error classes included, have JSDoc with an `@example`. Exported types have JSDoc without one, because the function that takes or returns the type already shows it in use. `tools/lint/src/publicApi.test.ts` reads every entry point except `./internal` with the TypeScript checker and checks this, the `is`, `has`, and `can` names, and that no public function takes a positional boolean. `tools/lint/src/examples.test.ts` type-checks every TypeScript block in the site's pages, the root README, the package READMEs, and the JSDoc `@example`s against package source. When an example uses a name it doesn't define, such as `request`, the test declares it, and when an example uses a `@portable/*` namespace without importing it, the test adds the import. An example therefore only needs the code a reader would copy. Other comments are rare: write one only when the code can't say why, and run the `no-comments` skill before you finish a change.

## Tests

- Tests live in `packages/<name>/test/`, a private workspace package (`@portable/<name>-test`) whose `package.json` holds the libraries we compare against, so the published package lists none of them. The package's own `devDependencies` hold only its optional peers, such as @noble/hashes, which its source needs to type-check. Tests import the package by name (@portable/lines), as a caller would, and import unexported code by path (`../src/DecoderStream.js`) only when it needs its own tests. `*.conformance.ts` runs in Node and in browsers, so put tests there unless they need one runtime. Put a test that needs a `node:*` server, such as the tests of the sockets Node adapter, in `*.conformance.test.ts`, which runs in Node, Bun, and Deno but not in browsers. `*.oracle.test.ts` runs only in Node and compares output with the library being replaced. `*.bench.ts` holds benchmarks, and also any test that compares timings (such as a linear-time check), because timing tests fail when the machine is loaded.
- Every package has a `*.bench.ts` that covers each public function and stream on realistic input, so a later performance pass has a baseline. Compare with the replaced library and with a native API where one exists. The README tables leave out code you'd write by hand from several platform calls, because it can be written many ways. When neither exists, still benchmark our own code.
- `test/<name>.fuzz.conformance.ts` holds the package's fuzz tests: fast-check properties run through `fuzz()` from @portable/fuzz (`tools/fuzz`), which takes the run count from `FUZZ_RUNS`. A parser or decoder gets random and mutated input and must return or throw only its documented errors, every encoder round-trips, and every stream gives the same output however its input is chunked. A package that keeps state, such as a queue or a rate limiter, gets a model-based test: `fc.commands` runs random sequences of calls on the package and on a small model of it, and compares the two after each call. `fuzz()` fails a run that takes longer than its `timeout` (2 seconds by default), so a quadratic slowdown or an async run that never settles fails the property. An infinite loop in sync code still hangs the test. `pnpm fuzz` runs them with many more runs. A bug the fuzzer finds gets a regression test with the concrete input in the normal conformance file.
- `test/<name>.fuzz.oracle.test.ts` holds differential fuzz tests, which run only in Node: they pass random or mutated input to our code and to the replaced library, and check that the results match whenever both accept the input. When the two differ on purpose for some input, such as an upstream bug listed in `PARITY.md`, leave that input out and say why in a comment.
- When a package replaces a library, design the package fresh and use that library's test suite as the list of cases to cover. `test/PARITY.md` maps each upstream test to our test for the same case, or gives the reason it doesn't apply.
- When a package replaces several libraries, build one API around what they have in common and let callers describe the differences, as webhooks does with scheme objects. Don't add a branch or option per replaced library.
- Also look for the replaced library's known traps: open and closed bug reports, edge cases its tests miss, and behavior its users complain about. Add a test for each one we handle differently, and list them under "Known upstream issues" in `PARITY.md`. An oracle test must not lock in an upstream bug.
- `test/inputs.conformance.ts` calls every function that takes bytes with each form in `byteForms` from @portable/fuzz: a plain `Uint8Array` and a `Uint8Array` that starts partway into a larger buffer. The second form makes the test fail if a function reads `bytes.buffer` instead of the bytes in the view's range. The test also writes each stream's chunks in each form. `toByteForm` builds each form, and the fuzz tests use `byteForm` to pick one at random.
- Load binary fixtures with `import.meta.glob('./fixtures/*', { query: '?url&inline', import: 'default' })` and `fetch` the data URL, as `packages/image-size/test/utils.ts` does. It works in Node and browsers for any file extension. Import a text fixture with `?raw`. Vite blocks `.pem`, `.key`, and `.crt` files in browser tests, so name such a fixture `.pem.txt`, as dkim does.
- Assert what a caller can observe. Read the `principle-test-behavior-not-implementation` skill before writing tests.

## Writing

Read the `technical-writing` and `unslop` skills (in `.agents/pstack/skills/`) before you write docs, READMEs, code comments, JSDoc, commit messages, or PR titles and bodies. These rules apply to all of them.

- Write the way you'd explain it to another engineer: in plain, specific words that keep the detail and the reason.
- Use the name that already exists: the symbol in the code, or a standard term a reader knows without looking it up (compare-and-swap, idempotent, B-tree). Don't paraphrase a known idea in a long clause, and don't swap detail for jargon either.
- Prefer the short phrase: "a missing blob", not "a blob that the bucket does not hold".
- Use literal verbs. "Is accepted" or "is stored", never figurative verbs such as "lands", "names", "absorbs", "wins", "rides along", or "stands on", or figurative nouns such as "seam". Don't personify code: a poll "needs" a deadline, it doesn't "want" one.
- Say what a thing does with its own verb: "a reader follows the head", not "the head is what a reader follows". A passive such as "is treated as body content" is fine when the actor is obvious.
- Keep words in the order a person would say them. Write "a CR without a following LF", not "a CR that no LF follows", which makes the reader work out who follows whom. Use the name a thing already has ("continuation lines") instead of describing it with a clause, and put a condition in an "if" or "when" clause instead of packing it into a noun phrase. Rewording an awkward sentence word by word keeps its shape: say the fact again from scratch.
- Don't invent an actor to state a fact or give advice. "An app that supports older browsers adds its own" and "a caller who wants a few tries writes a counter" describe nobody. Talk to the reader ("if you support older browsers, add them yourself") or name the real thing that acts (`Spf.check` reads the clock). This applies to commit messages, PR titles, and PR bodies too. `tools/lint/src/prose.test.ts` rejects "a caller who", "an app that", and similar phrases in Markdown and in source, and the commit-msg hook runs the same check on commit messages. Nothing checks a PR title or body, so read them for it before you open or edit a PR.
- Put a comma before the `and` or `or` that ends a list of three or more items: "`crypto.subtle`, `Blob`, and `fetch`", not "`crypto.subtle`, `Blob` and `fetch`". If an item has its own `and` or `or`, separate the items with semicolons or reword the sentence, so the reader can tell where each item ends. `tools/lint/src/prose.test.ts` checks lists in Markdown, comments, test names, and package descriptions, and the commit-msg hook checks commit messages. - Write package names as plain text, never in a code span or `<code>`, as in "mail builds on mime-headers and @portable/base64" and "the ws package". This covers Portable packages, the libraries they replace, and any other npm package. A subpath such as `@portable/streams/node` is an import specifier and stays code, and so does a line of code such as `import * as Base64 from '@portable/base64'`. In JSDoc, TypeScript reads an `@` after a space as the start of a tag, so write the package's short name there instead: "a `Dns.Resolver` from the dns package". `tools/lint/src/prose.test.ts` rejects a scoped name in a code span, a code span followed by "package", and a link to a package page whose text is a code span. - Say what the code does with a value: "stores" or "references", not a vague "names".
- Don't write rules as slogans or aphorisms ("a write lands only on the version it saw"). Name the mechanism.
- Don't join two separate facts into one sentence with ", and", especially when the second clause switches subject or voice ("Bytes go in and come out as `Uint8Array`, and a Node `Buffer` is accepted"). Give each fact its own sentence, or connect them with the reason that relates them.
- No "X. So Y. So Z." chains. Vary sentence length, and keep a cause and its effect in one sentence when they belong together.
- No AI vocabulary (delve, crucial, leverage), no "not just X but Y", no forced groups of three, no em dashes, no filler or hedging, and no clipped fragments with arrows.
- A commit message says why the change is made and what else was considered.
- Keep docs, comments, commit messages, and PR bodies blameless and neutral. Describe what the code does and why, not who asked for it, approved it, or wrote it, and don't name people or private projects and apps. Write "an audit of three apps that use Portable", not the apps' names.

### Two voices

Portable's prose has two voices. The rules above apply to both.

The pitch voice is for prose that explains why Portable exists: the intro of each site page, the opening of the root README, and the description at the top of each package README. Write it the way you'd explain Portable to a friend who builds web apps. It should read as human, conversational, concise, and casual.

- Say what changed or what hurts before you say what Portable is.
- Write "we" for the project and "you" for the reader. Contractions are fine.
- Name the pain concretely: "packages that only run in Node or only in browsers", not "compatibility issues".
- Keep Portable modest. Credit other packages when they already do the job, and say Portable fills the gaps.
- Keep one idea per sentence, and keep paragraphs to two or three sentences.
- A little warmth is fine ("We can finally write code once that runs anywhere", "please drop a note"). Hype isn't: no "blazing fast", "seamless", or "powerful".

This intro from the web platform page is in the pitch voice:

> All modern JavaScript runtimes include a rich set of web APIs. We no longer need to rely on packages that only run in Node or only in browsers, polyfill between them, or are compiled to Wasm. We can finally write code once that runs anywhere.

The reference voice is for prose that a reader consults to find a fact: API sections, options tables, JSDoc, the Conventions section of Getting started, and the docs in `docs/`. Write it plain and exact. State what a function does, what it takes, what it returns, and what it throws, and give the reason when the behavior could surprise a reader. Leave out the warmth, because it slows down a reader who is looking for one fact.

### Prose review

Before you finish a change that adds or edits prose, run the `prose-review` skill. A second agent reads only the prose the change adds or edits, checks it against this section, and suggests rewrites. When you also run `interrogate`, run this skill as well, because `interrogate` reviews the code and not the prose.
